## 4.2 Контекст системы и границы доверия

### Контекстная схема (текстовая, каноническая)

```text
[Owner в Telegram] -- HTTPS/Telegram API --> [C-08 Owner Gateway]
[C-08 Gateway] --> [C-01 Orchestration Core / Policy]
[C-01 Core] --> [C-02 Project Readiness] --> [GitHub readonly нормативные документы]
[C-01 Core] --> [C-03 Project Progression] --> [approved plan snapshot]
[C-01 Core] <--> [C-09 SQLite State Store + OperationJournal]
[C-01 Core] <--> [C-05 Resource Guard / systemd]
[C-01 Core] --> [C-06 AI Provider adapter: Codex CLI]
[C-01 Core] --> [C-07 Git and Test adapter]
[C-06 / C-07] --> [Developer isolated worktree / sandbox]
[C-06 / C-07] --> [Reviewer read-only snapshot / isolated test]
[C-07] <-- git + GitHub API --> [approved GitHub repository]
```

Ни Telegram, ни GitHub, ни LLM-вывод, ни содержимое репозитория не являются доверенным источником утверждений. Доверенная база — ранее зафиксированное решение владельца с проверенной личностью, scope и fingerprint нормативных файлов, хранящееся вне рабочего дерева AI. Рабочая копия проекта является недоверенной и не должна иметь полномочий самого оркестратора.

Контекст: один владелец, несколько добавленных репозиториев, один активный heavy worker; ограниченная очередь до 20 ожидающих задач. Первый пилот — Digital Core по фактически доступным утверждённым правилам (DEP-04); репозиторий-копия оркестратора не требует отдельной логики self-modification.

**IF-03 (adapter) [проектный контракт для КТ4]:** единственный **нормативный** набор request/response-полей, типов, обязательности, версии и обработку ошибок определяет **SPEC.md §9, IF-03**. ARCHITECTURE не создаёт альтернативную схему. Единые fixture для Developer/Reviewer: AC-F-12.1 и AC-F-16.1. Передача значений credentials запрещена.

**IF-04 (plan) — КТ3 APR-04, OQ-01 закрыт:** нормативный контракт находится только в SPEC §9: неизменяемый `IMPLEMENTATION_PLAN.md` с `plan_version` и таблицей `plan_item_id`, `req_ids`, `ac_ids`, `depends_on`, `deliverables`, `done_when`; JSON-массивы строк в Markdown-ячейках. Core читает утверждённый plan snapshot по SHA-256, хранит прогресс отдельно в SQLite; отсутствие/цикл/неизвестная ссылка → `PLAN_MISSING`/`PLAN_CYCLE`/`PLAN_AMBIGUOUS`, без запуска. Архитектура не определяет конкурирующую схему.

**IF-05 (side effect) [предложено]:** intent записывается и коммитится до внешней операции; remote outcome записывается отдельно; восстановление сверяет remote состояние. Для `idem_key` с другим `payload_digest` — `IDEMPOTENCY_CONFLICT`. Нельзя автоматически считать timeout доказательством неуспеха.

## 4.5 Хранение и модель данных

Единый владелец записей — C-09; прочие компоненты используют интерфейс хранилища и транзакции, не пишут независимые JSON-параллельные состояния. SQLite WAL, локальный защищённый том только для supervisor, миграции с фиксированной версией схемы.

| Сущность | Ключи и поля | Инварианты |
|---|---|---|
| Project | `project_id`, `repo_ref`, `base_sha`, `spec_digest`, `owner_approval_ref`, status | Допуск строго к версии и хешу; новый digest требует precheck |
| Task | `task_id`, `project_id`, `plan_item_id`, state, dependencies | Одновременно максимум один task в RUNNING-состояниях на сервер |
| Attempt | `attempt_id`, `task_id`, role, `input_sha`, `result_sha`, evidence | Независимая Git-проверка перехода Developer A→B и строгий Reviewer B→B, по SPEC §9 |
| Finding | `finding_id`, `ac_id`, evidence_ref, status | Закрытие только после нового независимого прогона |
| OwnerDecision | `decision_id`, `operation_digest`, exact_sha, decision | Старое approval не переиспользуется с другим payload/SHA |
| OperationJournal | `operation_id`, idem_key, payload_digest, state, remote_ref | Нет повторного side effect при UNCERTAIN до сверки |

Полная закрытая таблица `Project/Task/Attempt/Finding/OwnerDecision/OperationJournal`, guards и terminal/nonterminal статусы задаются только в SPEC §8.1 (уточнение Э6, предложение к КТ4); здесь не создаётся второе нормативное определение. `RESOURCE_BLOCKED` / `WAITING_DEPENDENCY` / `ARTIFACT_QUOTA_BLOCKED` — reason codes, не состояния. Внешние writes начинаются только после durable journal intent; при SQLITE_FULL/IOERR system fail closed без потери ещё живого intent; restart сверяет unresolved operations. Технический результат `APPROVED` допустим после независимого PASS обязательных проверяемых Reviewer AC на exact SHA; `NOT_CHECKED` пользовательского AC не является техническим blocker для Reviewer `APPROVE`, но **блокирует `COMPLETED` и запуск следующего зависимого этапа**. Если обязательная owner inspection в scope отсутствует, owner evidence не требуется; если она pending, задача переходит в существующий `AWAITING_OWNER`, и продолжение допускается только после аутентифицированного подтверждения владельца, актуального SHA/manifest/permissions и всех остальных обязательных AC PASS. Каноническая машина состояний остаётся только в SPEC §8.1. Merge лишь с решением владельца; изменения принятого SHA требуют регрессии (APR-04). Не допускается автоматическое `APPROVED` без проверки всех agent-checkable обязательных AC или автоматическое `PASS` owner inspection по ответу модели. Все дата-времена в UTC [предложено]. Метаданные ожидающей задачи ≤16384 байт; до 20 waiting tasks — 327680 байт payload без накладных расходов БД. Logs/evidence/worktrees квотируются отдельно: логи 7 суток/128 МиБ, локальные завершённые evidence 30 суток/512 МиБ; БД approvals и журнал UNCERTAIN вне LRU (APR-04). `ARTIFACT_QUOTA_BLOCKED` — backpressure без удаления protected evidence при отсутствии доказанной off-node копии; не запускать следующий heavy worker и не выдавать `APPROVED` при недоступном доказательстве (SPEC AC-N-15.2).

Backups: зафиксирована цель RPO ≤24 ч при потере узла, но пункт назначения резервной копии и проверенные средства восстановления пока неизвестны; требование к внешнему месту и восстановлению остаётся DEP-03. Для подтверждённых транзакций при падении процесса на исправном диске: RPO=0.

## 4.6 Развёртывание и среда

**Текущая цель:** Linux VPS 2 vCPU / 2 GiB RAM / около 20 GB disk, параллельно с работающим production Digital Core. Числа конфигурации представлены владельцем, read-only снимок 26.10.2026: `df -h /` показал 7,3 ГиБ свободно; `free -h` около 1,3 ГиБ available при 1,9 ГиБ total и 1 ГиБ swap; это моментальное наблюдение, не подтверждение допустимых лимитов worker. Выбор оставлять на текущем VPS условный: пока нет доказательства возможности изоляции и выделения лимитов, запрещён запуск unsafe worker. Production имеет приоритет; вмешательство в production-приложение/БД запрещено.

- Один supervisor `systemd` [утверждено AD-08]; worker ограничен cgroup CPU/RAM/числом процессов и файловыми/сетевыми правами.
- Отдельный системный субъект для worker; production-секреты, .env, бэкапы и данные DSC недоступны. Отдельные значения Linux UID/sandbox технологии [вариант полномочий утверждён APR-04; конкретная доступность sandbox не проверена, DEP-01].
- Рабочие каталоги по project/task, каждый scope проверяется Policy Gate; никакого shared writable path для Reviewer и live runtime.
- Зависимости фиксируются; приложение не обязано поддерживать постоянный Web UI, PostgreSQL, Kubernetes, Redis или очередь сообщений.
- Миграция данных и обновления — версионированные, с проверяемым восстановлением на тестовой копии; automatic self-update отсутствует.

**Приоритет дискового резерва:** нельзя занимать пространство, требуемое production и журналу, нельзя автоматически удалять чужие файлы. Объём доступного резерва и допустимые worker caps определяются DEP-01/OQ-04 с измерением, не предполагаются равными заданной RAM.

### Отказы: durable intent, evidence и OS isolation

1. C-09 фиксирует intent в отдельной завершённой SQLite-транзакции **до** внешнего побочного действия. C-07 не вызывается при невозможности подтверждения коммита intent.
2. При сбое в момент записи результата, после remote side effect, C-01 не ACK-ает операцию. На старте проверяет целостность БД и незакрытые journal intents, до remote reconciliation новых writes не делает. При неработоспособном SQLite — `FAIL_CLOSED`, ручная процедура recovery; попытка записи `UNCERTAIN` при полном диске не считается надёжной гарантией сама по себе.
3. C-05 проверяет собственные квоты и headroom перед worker; при достижении 512 МиБ без проверенной внеузловой копии — `ARTIFACT_QUOTA_BLOCKED`, без удаления forensic evidence. Дополнительные liveness/cleanup механизмы не должны нарушить приоритет production.
4. C-07/C-06 запускают недоверенный код под отдельным OS identity без supervisor/production mounts и secret environment; отрицательный тест проверяет реальные OS deny, а не только смоделированный результат. Timeout 7200/3600 с, process tree/cgroup завершается с эскалацией SIGTERM→SIGKILL; зависшие descendants не остаются (SPEC AC-N-13.2).

## 4.8 Решения КТ3 и открытые вопросы

**КТ3, APR-04:** OQ-01…07 закрыты пользователем; это детализация уже утверждённой архитектуры, без отмены AD-01…09 и CON-01…09.

- `IMPLEMENTATION_PLAN.md` — строго проверяемые шаги, REQ/AC и зависимости; утверждённый файл не меняется по ходу работы, прогресс хранится в SQLite.
- `OwnerDecision` включает подписанный данным владельцем manifest точных SHA-256 SPEC, ARCHITECTURE, AGENTS, PLAN и baseline; изменение digest запрещает старт без повторного подтверждения.
- Технический APPROVE этапа не означает merge в protected main; следующий этап может двигаться в разрешённом workstream с полной регрессионной перепроверкой затронутого SHA.
- Локальные логи ≤7 суток/128 МиБ, копии evidence ≤30 суток/512 МиБ; журнал операций, состояние и owner approvals нельзя удалять LRU; 7 ежедневных внеузловых backup должны быть проверены до эксплуатации.
- Codex 7200 секунд/вызов; тесты 3600 секунд/запуск; число циклов исправления не ограничено. `/pause` применяется после безопасной точки; неизвестное внешнее действие не повторяется вслепую; безопасные read — максимум 2 дополнительных повтора.
- Reviewer — независимый изолированный стенд с синтетическими данными и без права записи проверяемого исходника; CI обязателен для сканирования секретов.
- Supervisor-only credentials, отдельные минимальные роли; небезопасная или непроверенная изоляция блокирует worker.

**Решение Э6 APR-05 / OQ-08 [утверждено]:** GitHub Flow, protected `main`, тематические ветки и PR, без обязательного подписания коммитов, без разрешения на автономные merge/deploy. Подписание возможно добровольно; release-tag policy отдельно пока не утверждена, тегирование исключено из разрешённых AI-действий. **Решены OQ-09/A (APR-06) и OQ-10/A (APR-07):** утверждён тестовый профиль (Python 3.12.x, pinned CLI/deps, isolated test-only environment, exact PASS-команды) и политика ротации MVP (≤90 суток либо раньше provider expiry). Запуск тестов будущего кода и проверка production изоляции относятся к предэксплуатационным gates, но нормативная методика должна быть согласована до `READY_FOR_APPROVAL`. Фактические DEP-01…05 являются проверками перед эксплуатацией.

## 4.9 Качество архитектуры

### 4.9.1 Драйверы

Приоритет: (1) защита production, (2) отсутствие потери и повторов, (3) расширяемость по провайдерам и интерфейсам, (4) независимое ревью, (5) предсказуемая эксплуатационная стоимость. Масштаб: один владелец, ≥2 зарегистрированных проекта, 1 активная инженерная задача, до 20 waiting. Рост: новые CLI/API providers, Web UI, удалённые workers — не входят в MVP. Цена эксплуатации: VPS, inference/CLI quota и внешнее резервирование; значения без текущей проверки не записываются как факты.

### 4.9.2 Атрибуты, меры и испытания

| Атрибут | Меры | AD/CON | Независимая проверка |
|---|---|---|---|
| Расширяемость | AI provider и owner gateway адаптеры с версионируемыми контрактами | AD-01/03/06, CON-03 | Заменить fake AI adapter, core diff=0, пройти эталонный task |
| Надёжность | Atomic commits, журнал side-effects, UNCERTAIN/reconcile, ограниченная очередь, RPO/RTO от момента process failure до обслуживания | AD-02/09, CON-05 | Kill после remote operation до ACK: 0 повторов, Task сохранился |

### 4.9.4 Сценарии отказа и сохранность

| Внешняя зависимость/ресурс | Вызов и допустимый отказ | Поведение | Потеря принятых данных |
|---|---|---|---|
| Codex CLI | rate limit/crash/timeout | Сохранить Attempt, ограниченный retry, затем WAIT/BLOCKED | Нет при целой БД |
| GitHub | API timeout/503/неизвестный outcome push/PR | Записать UNCERTAIN; сверить SHA/ветку/PR до повторного write | Нет; external side effect не повторяется вслепую |
| Telegram | Bot API offline | Owner decision остаётся ожидающим; сообщение retry/dedupe | Нет |
| systemd/cgroups | Guard отказал или worker вышел за лимит | Resource blocked и остановка отдельной задачи | Нет подтверждённых записей, незавершённая работа требует reconciliation |
| SQLite/process | Аварийное завершение процесса | Restart на исправном хранилище, сверка состояний | RPO=0 для acknowledged транзакций |
| VPS disk failure | Недоступен том | Восстановление из внеузлового backup | RPO≤24 ч при работоспособном backup; зависит от DEP-03 |
| Disk full | Работа невозможна | Не запускать worker, запрет автоудаления чужих данных | Нет при возможности устойчивой записи; если отказала БД, операция не ACK |

**Ёмкость:** очередь 20 задач, до 16 КиБ метаданных каждая. Предельное время отказа внешнего сервиса не фиксируется; на переполнение — явный `QUEUE_FULL`. Новые задания после насыщения не считаются принятыми. Для долгих отключений данные уже принятых задач сохраняются в SQLite по правилам APR-04.

### 4.9.7 Секреты: имена, назначение, среды и ротация

| Имя [предложено] | Назначение | Субъект/права | Среда/хранение | Отзыв/ротация |
|---|---|---|---|---|
| `TELEGRAM_BOT_TOKEN_REF` | Исходящие блокирующие уведомления и чтение owner command | Только gateway supervisor, без агента | защищённый manager/env, не в проекте | Долгоживущий: ротация ≤90 суток; при утечке/смене доступа немедленный отзыв и замена; gate не допускает просроченный ref |
| `GITHUB_WRITE_CREDENTIAL_REF` | Разрешённые branch/PR operations | Узко ограниченный Git adapter, без merge/admin | Раздельные test/stage; вне рабочего дерева | Долгоживущий: ≤90 суток либо раньше истечения провайдера; short-lived: обновление до TTL; compromised → немедленный отзыв/блокировка |
| `CODEX_AUTH_REF` | CLI execution | Только выделенный runner, без передачи в test subprocess, не production | Безопасный локальный credential store | Долгоживущий: ≤90 суток либо ранее expiry; provider-managed session: re-auth/refresh к TTL, проверка полномочий ≤90 суток; при неподдерживаемой процедуре — owner APR по S8, до того BLOCKED |
| `OWNER_TELEGRAM_ID` | Определение owner identity, не credential-секрет | Gateway/auth policy | Конфигурация, не токен | Не периодическая ротация; по authenticated owner change немедленный отзыв прежнего ID, фиксация метаданных без секретов |

Здесь **нет значений**. В частности, никаких actual passwords/tokens/keys/cookies не запрашивать. Команды чтения системных секретов не выполнялись. OQ-07 (разделение полномочий) закрыт APR-04; реальные механизмы storage/sandbox и поддержка ротации ещё проверяются по DEP-01/02/05.

**Нормативная процедура S8 (вариант OQ-10/A одобрен владельцем APR-07 для MVP; итоговый пакет до КТ4 DRAFT):** gate перед каждым credential-dependent внешним действием сопоставляет `last_rotated_at`, `expires_at`, `next_due_at`, `revoked_at`, actor, environment, scope из supervisor-only inventory; отсутствие необходимых timestamp либо overdue/отзыв → deny до отправки, owner notification с метаданными, без значения секрета. Время `next_due_at = min(last_rotated_at + 90 calendar days, provider_expiry)` для долгоживущих; short-lived provider-managed — автоматическое обновление к TTL и проверка права доступа не реже 90 суток. Владелец или допущенный оператор через официального провайдера (вне Developer/Reviewer) создаёт replacement со строго ограниченными правами, обновляет supervisor reference, проверяет allowed/denied synthetic actions и отзывает прежний; при компрометации deny/revoke немедленно до выдачи нового. Только метаданные процедуры попадают в audit. Провайдер, запрещающий данную процедуру, требует owner-approved равноценную альтернативу через APR S8; без APR интеграция блокируется. Детерминированный oracle `AC-N-SEC-05.5` проверяет valid→overdue/compromised→replaced/old-denied без реальных секретов. Срок 90 суток — **утверждённый вариант OQ-10/A (APR-07) на время MVP**. Вариант B не выбран и не может включаться автоматически; для любых исключений или будущего изменения политики нужны отдельные CR/APR, а при несовместимости провайдера — BLOCKED до решения владельца. Обязательный `AC-N-SEC-05.5` включает проверки `now < next_due_at` (allow только при всех guards), `now == next_due_at` / `now > next_due_at` (deny), отсутствующий `last_rotated_at` или `next_due_at` (deny), более ранний provider expiry (deny начиная с expiry), revoked/compromised (deny), старый ref после замены (deny), новый корректный ref (allow). Используются синтетические UTC timestamps, без чтения секрета.
