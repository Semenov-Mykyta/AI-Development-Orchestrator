## 0.1. Оценка идеи

Проблема: ручное управление передачей заданий Developer/Reviewer, верификацией SHA и циклом исправлений требует регулярного участия владельца. Ценность: автономное продвижение по утверждённому ТЗ без самовольного изменения архитектуры. Альтернативы: готовые агенты и GitHub-ориентированные процессы; они не гарантируют соблюдения индивидуальных approval gates без дополнительной реализации. Решение: ограниченный модульный монолит, один рабочий цикл одновременно. Риски: недоверенный код, возможный конфликт с production на VPS, лимиты CLI, обрывы внешних действий. Идея принята для продолжения на КТ0; объём MVP зафиксирован на КТ1.

## 1. Назначение, цели и результат

### 1.1 Проблема
Владелец вручную маршрутизирует задачи между AI Developer и независимым Reviewer, запускает тесты, сопоставляет SHA и отслеживает повторные исправления, даже если его решения не требуется.

### 1.2 Цель
Самостоятельно вести разработку разрешённого GitHub-проекта по уже утверждённым SPEC/AGENTS/ARCHITECTURE и плану, сохраняя контроль владельца над изменением полномочий и production.

### 1.3 Наблюдаемый результат
Владелец добавляет репозиторий; после прохождения readiness gate система выбирает следующий допустимый этап по плану, запускает Developer, проверки и Independent Reviewer, возвращает замечания и продолжает работу, сохраняя доступ к статусу по запросу. В штатном случае автоматических уведомлений об успехе нет.

### 1.4 Метрики успеха (целевые значения на испытания MVP)

| Метрика | Исходное значение | Цель [предложено] | Проверка |
|---|---|---|---|
| Ручная пересылка Developer↔Reviewer | Требуется | 0 ручных пересылок на эталонной задаче с одним раундом исправления | UC-02, AC-F-13.1 / F-17.1 |
| Потеря принятых задач после рестарта процесса | Не измерено | 0 при целой БД | AC-N-04.1 |
| Уведомление о штатном успехе | Сейчас ручной процесс | 0 в эталонном успешном цикле | AC-F-23.1 |
| Непроверенные AC при статусе «завершено» | Не измерено | 0 | AC-F-18.1 |

## 2. Границы

### 2.1 Входит в MVP
- Добавление нескольких разрешённых GitHub-репозиториев и хранение их конфигурации.
- Обязательный readiness gate: только утверждённый, полный пакет SPEC/AGENTS/ARCHITECTURE (для M/L), план и зафиксированные основания утверждения; соответствие утверждённым требованиям применяется ко всем проектам.
- Выбор этапа по утверждённому плану, с учётом зависимостей и состояния выполненных проверок.
- Codex CLI в отдельных сессиях Developer и Reviewer; проверяемый точный SHA; локальные и тестово-интеграционные проверки.
- Контролируемые Git commit, push и PR в разрешённых ветках; merge/deploy исключительно после owner approval и через отдельно авторизованное действие; AI не получает production-права.
- Telegram-команды владельца, статус по запросу и блокирующие уведомления.
- Транзакционное хранение задач, журнал внешних действий, рестарт и восстановление.
- Одно активное инженерное задание, ограниченная очередь, защита ресурсов VPS.
- Работа с существующим или новым репозиторием, включая копию исходников оркестратора как независимый проект, без специальной self-modification логики.

### 2.2 Не входит в MVP
- Самостоятельное создание/утверждение ТЗ и плана при их отсутствии, автоматическое изменение требований.
- Подключение Claude/Gemini и прямых API, Web UI, полноценная параллельная обработка задач, автоматическая миграция VPS, коммерческая аналитика.
- Разрешение production-доступа агентам, автоматические merge и deploy, автоматическая чистка чужих каталогов, bypass проверок.
- Непроверенная совместимость с любым репозиторием и любым набором тестов; каждый проект проходит допуск.

### 2.3 Поставляемые артефакты (после КТ4)
Исходный код, зависимости с lock-файлом, тесты с трассировкой AC, CLI/Telegram инструкции, README по запуску и восстановлению, пример конфигурации без секретов, эталоны проверок, журнал соответствия для каждого PR/релиза, доказательства отрицательных тестов, проверенный пакет развёртывания без production-учётных данных.

## 6. Сценарии использования

**UC-01: Новый проект.** Owner указывает URL и scoped-допуск; система проверяет полный SPEC/AGENTS/ARCHITECTURE/plan, approvals и SHA; при PASS выбирает первую задачу; при FAIL сохраняет BLOCKED и отправляет один запрос. REQ-F-01…08, 24, 32.

**UC-02: Итерация исправления.** Developer создаёт технический SHA, выполняются AC, Reviewer в отдельной read-only сессии проверяет SHA; доказанный finding возвращается Developer; проверяется новый SHA; в финале готовится разрешённый PR без сообщения об успехе. REQ-F-12…23, 33.

**UC-03: Существующий репозиторий.** После фиксации owner-approved baseline и контракта обратной совместимости определяются незавершённые плановые этапы. REQ-F-34.

**UC-04: Разрыв связи в момент публикации.** Push прошёл, подтверждение не записано; после перезапуска журнал и remote сверяются; повтор без проверки запрещён. REQ-F-29…30.

**UC-05: Недостаточно ресурсов.** Действующий production сохраняет приоритет; не начинается новая тяжёлая задача; владельцу сообщается только при требуемом решении. REQ-F-31.

**UC-06: Нельзя закончить безопасно.** Даже после многократных исправлений запрещённый обход (отключение security gate, пропуск AC или повышение прав) отвергается. Если безопасный способ продолжить ещё существует, Developer может продолжать без лимита раундов; когда допустимого выхода нет — запрос владельцу с доказательствами, без обхода обязательных защит. REQ-N-12, REQ-F-17/19/24.

### 8.1 Закрытые машины состояний и guards (на проверку КТ4)

**Общие правила:** каждое изменение состояния — одна SQLite-транзакция под supervisor; недопустимое ребро → `INVALID_STATE_TRANSITION`, 0 side effects; неизменные approval/операционные доказательства не удалять. `RESOURCE_BLOCKED`, `PLAN_CYCLE`, `ARTIFACT_QUOTA_BLOCKED`, `POLICY_DENIED`, `DEPENDENCY_UNAVAILABLE` — **reason codes**, не состояния. Состояние `PAUSE_REQUESTED` — устойчивый control flag проекта, не дополнительное состояние Task; `WAITING_DEPENDENCY` — reason code к `BLOCKED`, не состояние; `AWAITING_OWNER` — явное устойчивое Task state при необходимости решения владельца, включая обязательную owner inspection AC текущего этапа; её `PASS` записывает только supervisor по аутентифицированному, scoped и неустаревшему подтверждению владельца, но не Reviewer. Повторно требовать уже действительное owner evidence для каждой задачи не нужно: повторная инспекция требуется при изменении охваченных условий/прав/среды, нормативных digests либо истечении утверждённой валидности evidence. Одно active Task (`PRECHECK|DEVELOPING|TESTING|REVIEWING|REWORK|UNCERTAIN`) на все проекты. Исключение: `REWORK` фиксируется между попытками, но занимает единичный слот только при запущенном worker; новая задача не стартует до завершения текущей фазы в рамках общей сериализации.

**Restart:** при старте всегда проверяются целостность SQLite, доступное место для её записи, нормативный digest и journal. Незакрытые `IN_FLIGHT`/intent без durable outcome рассматриваются как `UNCERTAIN` независимо от старого статуса Task; **перед запуском любого нового external write** требуется сверка. При недоступной БД или journal вход в глобальное read-only `FAIL_CLOSED` (не отдельное состояние Task), никаких внешних write или новых worker; требуется восстановить возможность безопасного чтения/записи, затем сверить. Потеря ACK не доказывает отсутствие побочного действия. Из `COMPLETED`, `FAILED`, `RETIRED` автоматических обратных переходов нет; изменение требует новой approved задачи/CR, а не подмены истории.

**Проверка переходов:** AC-N-04.2 (Т, [предложено]): table-driven тесты всех строк таблицы и запрещённых рёбер; двойной claim → один рабочий slot; `PAUSE_REQUESTED` переживает kill/restart, `UNCERTAIN` не повторяет write и не возобновляется через `/resume`; terminal states неизменны.

**Контроль evidence и write-ahead при ошибках диска [уточнение Э6]:** ни один внешний write не начинается без устойчиво подтверждённого `INTENT_COMMITTED` и проверки доступности журнала; любой сбой записи SQLite не является успешным ACK. При рестарте intent без durable outcome трактуется как неизвестный результат до независимой сверки remote. Когда локальный лимит evidence достигнут и нет проверенной внешней копии, наступает `ARTIFACT_QUOTA_BLOCKED`: новые тяжёлые операции не запускаются, подтверждения AC не выдаются, ценные доказательства не удаляются. Уже исполняемый worker доходит до управляемой точки остановки; если доказательства нельзя устойчиво сохранить, AC = `NOT_CHECKED`, не PASS. Никакой механизм не удаляет файлы вне разрешённого каталога; внешний backup должен подтверждать целостность восстановлением на тестовом узле.

**Резервирование:** копия БД и необходимых метаданных вне VPS не реже раза в 24 ч (предложено и подтверждено APR-03); место хранения и способ защищённой доставки — DEP-03 (проверяется до ввода в эксплуатацию); хранить последние семь ежедневных внеузловых снимков согласно APR-04. Миграции схем версионированы; импорт реальных production-данных не входит в MVP. Никаких значений секретов в таблицах или резервных копиях документации.

**IF-03: единственный нормативный контракт AI Adapter v1 [проектный, для КТ4].** Для обеих ролей обязательные поля request: `schema_version="1"`, `role∈{developer,reviewer}`, `project_id` (ID проекта), `task_id` (ID задачи), `spec_digest` (SHA-256 утверждённого SPEC, 64 hex), `input_sha` (полный hex40 Git commit, который Supervisor независимо прочитал из разрешённого репозитория и закрепил для *этой попытки*), `workdir` (относительно разрешённого изолированного root), `allowed_scope` (непустой конечный перечень разрешённых путей/операций), `policy_digest` (SHA-256 доверенной supervisor policy, 64 hex), `timeout` (положительное целое число секунд; для Codex ≤7200). `input_sha` означает **base_sha конкретной Developer-попытки** либо **exact reviewed SHA для Reviewer**, а не неизменяемый исходный onboarding `Project.base_sha`. Ни одно поле не содержит значений credentials или путей к секретам; рабочий каталог может находиться только в разрешённом изолированном root. `allowed_scope` не расширяет доверенную supervisor policy. Запрещено наследовать model-supplied значения из ответа как разрешения на Git-операцию.

Response v1 для обеих ролей имеет обязательные поля `schema_version="1"`, `attempt_id` (уникальный, сопоставляемый с созданной Supervisor попыткой), `exit_code` (целое либо `null`, если запуск не состоялся), `result_ref` (ссылка на артефакт либо `null`), `input_sha` (точная копия request.input_sha), `result_sha` (полный hex40 проверяемого commit), `evidence_refs` (массив ссылок, может быть пустым лишь при неуспешном/не начатом запуске), `error_kind` (`null` либо `TIMEOUT`, `RATE_LIMIT`, `INVALID_OUTPUT`, `POLICY_DENIED`, `EXECUTION_ERROR`). Response `spec_digest` не является источником доверия и не заменяет проверку заранее одобренного snapshot. При успехе `exit_code=0`, `error_kind=null`, `result_ref` и обязательные evidence присутствуют; exit=0 сам по себе **не** означает ни пройденные AC, ни Reviewer `APPROVE`.

**Различие ролей (без второй версии schema):** Developer может создавать новый commit `B` из `input_sha=A`; **успешный результат с изменением кода** требует `result_sha=B`, где `B` — существующий immutable commit в разрешённом локальном Git-репозитории, достижимый из `A` через разрешённую историю текущей задачи, а изменения на пути A→B удовлетворяют scope, policy, branch и ограничениям утверждённого snapshot. Supervisor проверяет объект B, ancestry от A, tree/diff и соответствие task **самостоятельными Git-командами в доверенной среде**; `result_sha` только предложение адаптера, а не доказательство. Для неизменившей код Developer-попытки B=A разрешён только при явном отсутствии code changes; это не засчитывает исправление и не становится автоматическим `APPROVE`. Reviewer получает `input_sha=B` после указанной проверки и **обязан** вернуть `result_sha=B`; Reviewer не вправе создавать/подменять commit. Ни в каком случае response другого SHA, неизвестный commit, выход за scope или несанкционированный переход ветки не принимается и не передаётся следующему этапу; фиксируется `SHA_MISMATCH` / `POLICY_DENIED`, `0` продвижений Task и `0` опасных remote writes. Результат Reviewer без независимых AC не принимается независимо от совпадения SHA.

Неизвестная major schema version или отсутствующее/неправильно типизированное обязательное поле → `INVALID_ADAPTER_VERSION` / `INVALID_OUTPUT`; `input_sha` не совпадает с сохранённым Supervisor request либо `result_sha` не прошёл независимую Git-проверку/проверку роли → `SHA_MISMATCH` (нарушение scope также `POLICY_DENIED`). Все проверки до durable ACK, следующего агентского запуска и Git push; источник доверенного SHA — локально подтверждённый commit/ref и журнал Supervisor, **не** текст ответа модели. C-06 нормализует CLI-события провайдера, Core не читает внутренний формат Codex.

**Контрактные фикстуры IF-03:** `developer_A_to_B` (A→допустимый потомок B после независимой Git-проверки — ACCEPT), `reviewer_B_to_B` (exact SHA B на входе и выходе — ACCEPT), `forged_B_to_C` (подмена Reviewer, неизвестный/недостижимый C либо выход Developer за scope — REJECT), `developer_A_to_A` (нет изменений → допустим результат без приёмки исправления), `missing_spec_digest`, `wrong_input_sha`, `unknown_version`, `wrong_result_sha` — REJECT до продвижения Task, отправки следующему агенту и remote write. Эти эталоны являются частью `AC-F-12.1`, `AC-F-13.1`, `AC-F-16.1` и `AC-F-17.1`; ARCH §4.4 ссылается только сюда.

**IF-04: нормативный контракт плана v1 (APR-04).** Файл `IMPLEMENTATION_PLAN.md` содержит единственную машиночитаемую таблицу с колонками `plan_item_id`, `req_ids`, `ac_ids`, `depends_on`, `deliverables`, `done_when`. Списки — JSON-массивы строк в ячейках Markdown (экранирование символа `|` по Markdown), пустой список — `[]`. `plan_version` — строка SemVer в начале файла. Все ID уникальны; зависимости указывают только другие `plan_item_id`, циклы и неизвестные ссылки вызывают `PLAN_AMBIGUOUS`/`PLAN_CYCLE`. Результаты выполнения не записываются в утверждённый файл: state и evidence пишутся только в SQLite/отчёты. Пример входа: A (`req_ids=["REQ-F-01"]`, `ac_ids=["AC-F-01.1"]`, `depends_on=[]`), B зависит от A; после принятия A становится допустим B. Смена одного байта утверждённого плана инвалидирует digest.

**IF-06: владелец подтверждает нормативный manifest v1 (APR-04).** В supervisor-only хранилище сохраняются `{approval_id, owner_id, approved_at_utc, base_sha, spec_sha256, architecture_sha256, agents_sha256, plan_sha256, baseline_ref}`; approval не выдаётся CLI/worker. При подмене одного байта любого нормативного файла — `APPROVAL_STALE`, 0 запусков. Владелец через собственный authenticated interface подтверждает конкретный manifest, а не надпись `APPROVED` внутри репозитория.

**Позитивный IF-02:** decision_id существует, SHA совпадает, authenticated owner нажимает approve → ровно одна запись approval, открывается только конкретное действие. **Негативный IF-02:** SHA иной → `STALE_DECISION`, 0 внешних действий. **Позитивный IF-04:** A без зависимостей, B зависит от A → A выбирается первым. **Негативный IF-04:** A зависит от B, B от A → `PLAN_CYCLE`, 0 запусков. Это ожидаемые результаты, не выводимые из кода.

**OQ-05 — решение пользователя, APR-04:** один запуск Codex не более 120 минут, один запуск тестов не более 60 минут, фиксированного лимита раундов Developer/Reviewer нет. Нельзя ради продвижения обойти REQ/AC/CON/AD; при отсутствии безопасной альтернативы запросить решение владельца (не bypass абсолютных правил). **Срединный сбой для всех мутирующих операций:** register project, state transition, Git branch/commit/push/PR, owner approval, очереди и внешние уведомления тестируются инъекцией сбоя *перед записью, после локальной записи и после неизвестного внешнего результата*. Идемпотентность и отказ от перезаписи чужих объектов обязательны. Нормативная политика: один вызов Codex 7200 с, один тестовый запуск 3600 с; безопасный read допускает максимум два дополнительных повтора. Timeout прерывает процесс с фиксацией `NOT_CHECKED` для незавершённого теста; нельзя пропускать проверку.

Интервалы календарных дней считаются на UTC-aware timestamps в синтетических fixtures по согласованному OQ-10; недопустимо округление «ровно срок» вниз. Инспекция подтверждает метаданные, ответственного, независимый расчёт due, событие отзыва и 0 утечек. Несоответствие любого из восьми ожиданий = FAIL. | И, Т, И (пользователь), Т+И |

**Политика S8 — утверждённый выбор владельца OQ-10/A (APR-07; для MVP; пакет в целом DRAFT до КТ4):** канонический реестр в ARCHITECTURE §4.9.7. Для долгоживущих секретов `TELEGRAM_BOT_TOKEN_REF`, `GITHUB_WRITE_CREDENTIAL_REF`, `CODEX_AUTH_REF` обязательная плановая ротация не реже одного раза в **90 календарных суток (OQ-10/A, APR-07)** с даты `last_rotated_at`, а если установлен срок истечения провайдера — до его истечения, что наступит раньше. Для автоматически выдаваемых краткоживущих credentials ротация происходит при каждом истечении по провайдерскому TTL, при проверке сроков доступа не реже одного раза в 90 суток. Если штатная модель конкретного провайдера **не позволяет** такой порядок, использование блокируется до явного решения владельца о равноценной мере через APR по S8; это не разрешение агенту обойти gate. При подозрении на утечку, компрометацию, отзыве полномочий, смене оператора/среды или изменении scope — **немедленный** отзыв в доступном интерфейсе провайдера и замена перед повторным использованием; отсутствие возможности отзывать означает немедленную блокировку зависимой интеграции. Безопасная процедура: оператор с соответствующими правами вне AI создаёт новый credential в том же ограниченном scope и среде, внедряет supervisor-only reference вне agent workspace, проверяет тестовыми разрешёнными и запрещёнными операциями, отзывает старый credential и удостоверяется в запрете его дальнейшего использования; при компрометации сначала блокировка/отзыв, потом выпуск замены. Учёт содержит только ref, среду, scope, владельца, `last_rotated_at`, `expires_at`, `next_due_at`, `revoked_at` и идентификатор одобрения — **никогда значение**. В утверждённом для MVP варианте OQ-10/A просрочка или неопределённый due запрещают credential-dependent outbound operation (`WAITING_DEPENDENCY`/`BLOCKED` с кодом причины). `OWNER_TELEGRAM_ID` — не секрет и не подлежит периодической ротации: его изменение допускается только через аутентифицированное решение владельца, с отзывом прежней авторизации и тестом отказа старому ID.

Места хранения (только имена и ссылки; APR-04, точная работа sandbox проверяется DEP-01/05): `CODEX_AUTH_REF`, `GITHUB_WRITE_CREDENTIAL_REF`, `TELEGRAM_BOT_TOKEN_REF`, `OWNER_TELEGRAM_ID` — конкретное безопасное именование [предложено], менеджер секретов и способ внедрения в разные процессы — APR-04 (supervisor-only хранилище, scoped-раздача; детали ОС проверяются DEP-01/05). Ни одно значение не хранится в документах, промптах и журналах.

## 14. Критерии приёмки и Definition of Done

Каждая запись `REQ-F`, `REQ-N`, `REQ-N-SEC`, `ERR` имеет AC в соответствующей таблице. AC записывается до кода. Эталонные данные и ожидаемый результат фиксируются в этой спецификации; тесты с методом Т обязаны выполняться автоматически. Метод И/Д/А не замещается «верим разработчику». По всем интеграциям INT-01…04 — минимум одна проверка против утверждённого тестового окружения.

**Результат приёмки MVP:** тестовая задача проходит `Developer → Tests → Independent Reviewer → REWORK → Tests → технический APPROVED → (обязательное owner AC, когда применимо) → COMPLETED → сохранение прогресса` с доказательствами точного SHA; тесты отказов не дублируют опасные операции; запрещённый доступ не удаётся; штатных инициативных Telegram-уведомлений 0. Сборка воспроизводима, отчёт REQ/AC с результатом PASS/FAIL/NOT_CHECKED обязателен для каждого PR и релиза. Секреты отсутствуют. Для проекта также действует принцип невозможности bypass ради PASS по REQ-N-12. Не все AC могут быть проверены до реализации: это программа будущих испытаний, не доказательство текущего PASS.

**Граница приёмки пользовательских AC:** технический `APPROVE` Reviewer не заменяет проверку `проверяет пользователь`. Для каждого этапа supervisor вычисляет обязательные AC и части смешанных методов Т+И по утверждённому плану и действующим условиям; любой обязательный owner AC `NOT_CHECKED`/`FAIL` запрещает `COMPLETED` и старт следующего зависимого этапа. Необходимое подтверждение владельца хранится как scoped evidence с датой и проверяемой связью с актуальной средой/правами/manifest/SHA; подтверждение старой конфигурации не переносится автоматически. Если owner AC или owner-часть смешанного метода не требуется в scope этапа и ранее сохранённый PASS не устарел, нового ручного подтверждения не требуется. Реальная приёмка и runtime-испытания — после реализации; в этом DRAFT они `NOT_CHECKED`.

## 19. Глоссарий

| Термин | Значение в этом ТЗ |
|---|---|
| `APPROVED` (Reviewer/Task) | Только технический итог exact-SHA проверки всех обязательных agent-checkable AC; owner AC с `NOT_CHECKED` не становится PASS. Не разрешает COMPLETED/следующий этап/merge/deploy и не является КТ4 |
| `COMPLETED` (Task) | Терминальное завершение лишь после всех обязательных AC в scope `PASS`, включая аутентифицированное подтверждение пользователя для помеченных AC, и durable snapshot; merge в `main` не подразумевается |
| `AC` | Бинарный проверяемый критерий приёмки с ID, методом и независимым эталоном |
| `REQ` | Нормативное функциональное (`REQ-F`) или нефункциональное (`REQ-N`) требование |
| `APR` | Запись явного согласования владельца конкретного объекта и версии; не выводится из `APPROVED` внутри недоверенного репозитория |
| `AD` / `CON` | Архитектурное решение / обязательное ограничение, подтверждённые пользователем в рамках КТ2 |
| `OQ` / `ASM` / `DEP` | Открытый вопрос / допущение / зависимость; закрытый OQ не считается проверенным runtime-тестом |
| `Readiness Gate` | Формальная и смысловая проверка утверждённого нормативного пакета до запуска задачи |
| `PENDING_PRECHECK` | Начальное состояние Project сразу после регистрации, до результата readiness |
| `ADMISSION_BLOCKED` | Состояние проекта при недостающем или неутверждённом нормативном пакете или неподтверждённых ресурсах |
| `AWAITING_OWNER` | Устойчивое ожидание точного решения владельца либо обязательной owner inspection AC, привязанной к scope/датe/версии; до PASS итоговое COMPLETED и зависимые задачи запрещены |
| `UNCERTAIN` | Действие могло иметь внешний side effect, но его подтверждение не получено; до независимой сверки повтор запрещён |
| `REWORK` | Состояние возврата задачи Developer после исправимого фактического нарушения |
| `OperationJournal` | Транзакционный журнал с durable intent до внешнего write и сверкой результата после возможного сбоя |
| `idempotency key` | Уникальный ключ действия, привязанный к payload digest; тот же ключ с иной нагрузкой вызывает отказ |
| `spec_digest` | SHA-256 утверждённого пакета, привязанный к решению владельца; не ссылка на версию файла в чате |
| `worktree` | Отдельный Git working tree для разработки/проверки; сам по себе не OS sandbox |
| `worker` / `sandbox` | Дочерний исполнитель / принудительно изолированное ОС-окружение без production-разрешений |
| `Review Round` | Повтор Developer → Reviewer; количественного предела нет, безопасность и разрешения не ослабляются |
| `OQ-09` / `OQ-10` | Закрытые решением владельца вопросы тестового профиля (APR-06) / плановой ротации для MVP (APR-07); не являются доказательством выполнения тестов или КТ4 |
