## Обязательные правила приёмки

- Каждый `REQ/ERR` из SPEC §§5, 7, 12, 13 и каждый его `AC` присутствует **ровно в одном** основном пункте плана. Таблица не изменяет содержание требований, оракул AC или приоритет правил безопасности; все строки принимаются только при каждом AC PASS с указанным методом.
- **Security-first gates (не подлежат отсрочке):** P01 реализует обязательные защитные границы, secret scanning (в том числе CI), Policy Gate, осознанный отказ от bypass, изоляцию worker/test runner и resource/evidence admission на синтетическом стенде; P02 — durable journal, отказные состояния и безопасную сверку до внешнего Git. Отсутствие обязательного AC в P01/P02 = `BLOCKED` для P03/P04 (а не разрешение временно обойти защиту). P07 повторно проверяет, не создаёт защиту впервые. При реализации P03/P04 все эти проверки повторяются на интегрированных компонентах, и не могут быть waived по причине промежуточного этапа.

Порядок намеренно линеен ради одного активного тяжёлого worker; нет автоматического merge/deploy или публикации normative SPEC из реализации PR.
- Утверждённый вариант при реальном подключении хранит точные SHA-256 SPEC/ARCH/AGENTS/PLAN и baseline в owner-approved manifest вне workspace; утверждённый документарный baseline v0.13 не заменяет проверку фактической среды, permissions и owner manifest перед запуском.
- Все этапы, отчёты, эталонные данные и baseline должны быть согласованы перед запуском; GitHub Flow и отсутствие обязательной подписи коммитов согласованы APR-05 (OQ-08); тестовый профиль и метод PASS утверждены OQ-09/A (APR-06), фактическая среда и результаты ещё NOT_CHECKED.
- Изменение нормативной версии/плана только через CR и отдельный docs-only PR; активный прогресс не редактирует этот файл.

**Матрица приёмки:** метод и ответственный для каждого из 85 AC задаёт только SPEC в исходной таблице; SPEC §18 отображает тот же метод **без замены Д/И на Т**. Для `AC-N-10.1` и `AC-N-SEC-05.3` обязательную инспекцию владельца нельзя заменить тестовым mock. Reviewer `APPROVE` может быть только техническим при pending owner AC; этап не `COMPLETED`, следующий зависимый этап не начинается, пока подтверждение владельца с действующим scope/SHA/permissions не даст PASS. Негативный AC-F-18.1 закреплён в P03, переходы AC-N-04.2 в P02; приоритет security-first P01/P02 сохраняется. **Для первого построения P01** C-08/C-09 ещё не существует: единственный допустимый owner evidence gate — проверенное независимым Reviewer GitHub PR review от доверенного owner account на точные head SHA/manifest/scope и реальные метаданные прав, см. ARCH §4.6. Этот review не является owner decision уже работающего Supervisor; C-09 в P02 позже импортирует его только после независимого recheck, а P07 требует свежую инспекцию реально установленных доступов перед production. Отсутствие PR или remote-проверки не означает PASS и не допускает P02. Любое расхождение — `BLOCKED` для завершения соответствующего этапа.
